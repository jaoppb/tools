# Migrating from v0.1.0 to v0.2.0

Previous: none · Next: [v0.2.0 → v0.3.0](v0.3.0.md)

This guide covers what an adopter of the `v0.1.0` binaries, the composite GitHub Action or `tools.toml` has to know to move to `v0.2.0`. It describes `v0.2.0` as it shipped: three binaries (`issues-check`, `repo-sync`, `project-sync`) and the keys of the v0.2.0 `tools.toml`. Where a later release changed something again, the section ends with a **Later** note.

Every release gets one guide, `docs/migrations/<version>.md`, covering the step from the previous release only. Jumping several releases means reading the guides in order.

## Packaged CLI and composite GitHub Action (#39)

**What changed.** `v0.1.0` already published the `issues-check`, `repo-sync` and `project-sync` binaries on GitHub Releases. `v0.2.0` adds a composite action (`jaoppb/tools`, `action.yml` at the repository root) and `scripts/install-tools.sh`. Both download the release binary for the runner, verify its SHA256 checksum (the script skips verification with a warning when neither `sha256sum` nor `shasum` exists, and falls back to `cargo install --git` when a release asset cannot be downloaded) and cache it. Release assets are named `<tool>-v0.2.0-<target>.tar.gz` (`.zip` on Windows) with a matching `.sha256`, for Linux (`x86_64`, `aarch64`), macOS (`x86_64`, `aarch64`) and Windows (`x86_64`).

**What you must do.** Nothing breaks. To replace a hand-written download step, use the action. Inputs in v0.2.0:

| Input | Default | Meaning |
|-------|---------|---------|
| `version` | `latest` | Release tag to install |
| `tools` | `all` | Comma-separated `issues-check`, `repo-sync`, `project-sync`, or `all` |
| `install-dir` | `${{ runner.temp }}/tools-bin` | Where binaries are placed (added to `$GITHUB_PATH`) |
| `github-token` | `${{ github.token }}` | Token for downloads and audits |
| `cache` | `true` | Cache installed binaries across runs |
| `check-issues` | `false` | Run `issues-check` after install |
| `check-repo` | `false` | Run `repo-sync --check` after install |
| `issues-check-args` | `""` | Extra flags for `issues-check` |
| `repo-sync-args` | `""` | Extra flags for `repo-sync --check` |

Output: `installed-version`, `tools-dir`.

```yaml
- uses: actions/checkout@v4
- uses: jaoppb/tools@v0.2.0
  with:
    check-issues: 'true'
    check-repo: 'true'
    github-token: ${{ secrets.GITHUB_TOKEN }}
```

Without the action, from a checkout of this repository: `TOOLS_VERSION=v0.2.0 TOOLS_LIST="issues-check,repo-sync" ./scripts/install-tools.sh`.

**Later.** v0.3.0 consolidates the three binaries into one `tools` binary (#66); the action and release assets change with it. See [One `tools` binary](v0.3.0.md#one-tools-binary-66) and [Composite action inputs](v0.3.0.md#composite-action-inputs-63-66) in the v0.3.0 guide.

## Configurable milestone formats (#38)

**What changed.** The audit always required an open issue's milestone to be a release such as `v0.1.0`; teams that name milestones by phase or sprint could not pass the `milestone` rule (it reported `milestone is not a release`). `[github.issues.rules]` now takes `milestone_format`:

- `"semver"` (default): a release such as `v0.2.0`. Reports are unchanged (`milestone is not a release such as v0.1.0 or v0.2.0`).
- `"any"`: any title is accepted, including phase names.
- anything else: a regular expression the title must match somewhere. A title that does not match reports `milestone does not match the configured milestone_format`. An invalid expression is a configuration error.

**What you must do.** Nothing if your milestones are releases. Otherwise:

```toml
# before (v0.1.0): no way to accept "Phase 1"
[github.issues.rules]
milestone = true

# after (v0.2.0)
[github.issues.rules]
milestone = true
milestone_format = "^Phase [0-9]+$"   # or "any"
```

`milestone_format` only changes what the title may look like. `milestone = true` still requires every open issue to have one. The `release` rule, which orders issues across releases, only compares milestones that read as `vX.Y.Z`; with `"any"` or a regular expression it silently skips the others.

## Configurable area label prefixes (#32)

**What changed.** The `labels` rule required a label starting with exactly `area:`. It now accepts any prefix in `area_prefixes` (default `["area:"]`), and matching ignores case and accents, so `Área:segurança` or `área:api` satisfy `area:`.

**What you must do.** Nothing for the default. To use a different vocabulary:

```toml
# before (v0.1.0): only "area:" counted
[github.issues.rules]
labels = true

# after (v0.2.0)
[github.issues.rules]
labels = true
area_prefixes = ["area:", "domain:"]
```

The type label is still `type:` and is still required exactly once. `project-sync` reads the same `[github.issues.rules]`, so `area_prefixes` also applies to its Ready gate.

**Later.** In v0.3.0 the Project gate reads `[workflow.params] area_prefix` (a list) instead; `area_prefixes` stays for `tools issues check` until #59. See [Workflow engine and `tools config migrate`](v0.3.0.md#workflow-engine-and-tools-config-migrate-56-57-58).

## ADR/SPDD reference rules decoupled from the audit (#36)

**What changed.** `v0.1.0` hard-coded checks for the Cosmo project's ADR numbers and SPDD paths in issue and pull request text, enabled by default (`references = true`). They are removed from the audit in `v0.2.0`, together with their violation codes `old-adr-number` and `deleted-spdd-path`. `references` and `text` are still accepted by the parser but do nothing, and now default to `false`.

**What you must do.** Delete both keys. If you relied on the ADR/SPDD checks, they are gone; enforce them outside `tools`.

```toml
# before (v0.1.0)
[github.issues.rules]
references = true
text = true

# after (v0.2.0): remove them (still parsed, ignored)
[github.issues.rules]
```

**Later.** v0.3.0 rejects `references` and `text` (#60): leaving them in `tools.toml` becomes a configuration error. See [Removed rule keys are rejected](v0.3.0.md#removed-rule-keys-are-rejected-60).

## Per-repository label and milestone overrides (#34)

**What changed.** `repo-sync` can declare labels and milestones that apply to one repository only, in `[github.overrides.<repo>.labels]` and `[github.overrides.<repo>.milestones]`. Each target repository gets the shared `[github.labels]`/`[github.milestones]` plus its own overlay; repositories without an overlay get the shared declarations only, and an overlay for a repository that is not targeted is ignored.

**Merge rules.** `items` override by key (`name` for labels, `title` for milestones) and otherwise append; `deprecated` is a union; `renames` and label `migrations` merge key by key with the overlay winning (only `repo-sync` sees overlay `migrations`; `issues-check --migrate` reads the shared table); `prune_unmanaged` replaces the shared value only when set. The shared section is optional. An unrecognised key inside an overlay (say `prune_unmanged`) or the same item twice in one overlay is a configuration error.

**What you must do.** Nothing unless you want per-repository differences. v0.1.0 silently ignores a `[github.overrides]` table, so declare it only after every consumer runs v0.2.0.

```toml
# before (v0.1.0): every repository gets the same labels
[github.labels]
items = [{ name = "type:feat", color = "1d76db", description = "New behaviour" }]

# after (v0.2.0): add one label to "web" and recolour another
[github.overrides.web.labels]
items = [
    { name = "area:ssr", color = "2ea44f", description = "Server-side rendering" },
    { name = "type:feat", color = "00ff00", description = "Web feature" },  # replaces the shared item
]
```

See [Per-Repository Overrides](../multi-repo-onboarding.md#per-repository-overrides) for a fuller example.

**Later.** v0.3.0 replaces `prune_unmanaged` with a per-kind `unmanaged` severity and rejects the old key (#76). See [`unmanaged` replaces `prune_unmanaged`](v0.3.0.md#unmanaged-replaces-prune_unmanaged-76).

## Multi-repository targets (#11, #12, #37)

**What changed.** Issue identity became repository-qualified, so `app#1` and `web#1` no longer collide, and blockers and pull request links resolve across repositories. A target can list several repositories:

```toml
# before (v0.1.0): one repository
[github.repository]
owner = "acme"
name = "web"

# after (v0.2.0): several, all under the same owner; [github.repository] is still required
[github.repository]
owner = "acme"
name = "web"

[github]
repositories = ["web", "api", "app"]
```

On the command line, `--repo` can be repeated (`issues-check`, `project-sync`, `repo-sync`) and `--owner` has the alias `--org` on `issues-check` and `repo-sync` (not on `project-sync`). `repo-sync --org <org>` with no `--repo` and no `repositories` list is refused, so an organization is never synchronized by accident.

**What you must do.** Nothing for a single-repository setup. `repo-sync` now iterates every target repository, so with `repositories` set a bare `repo-sync` touches all of them: run `repo-sync --dry-run` first. With more than one target repository its output is split into sections prefixed `[<repo>]`; `--check` reports drift across all repositories and exits 1 at the end, while a read or write error aborts at once with exit code 2 and a `[<repo>]` prefix. Adjust anything that parses that output or relies on those exit codes.

## Organization-owned Projects V2 (#10)

**What changed.** The Project lookup tried only a user-owned Project V2. It now resolves a Project owned by either a user or an organization.

**What you must do.** Nothing. If `[github.project]` pointed at an organization's board and failed in v0.1.0, it works now.

## Project status mapping and optional fields (#13)

**What changed.** Project status names are matched case-insensitively, and `[github.project.status_mapping]` maps your column names onto the canonical `Backlog`, `Ready`, `In progress`, `In review`, `Done`. An unknown target is a configuration error that lists the valid ones. `Priority` and `Effort` fields are optional unless the `priority`/`effort` rules are switched on. **Default changed:** in v0.1.0 the Ready gate always required Priority and Effort (and a small enough Effort); in v0.2.0 both rules default to `false`, so an upgrade silently loosens the gate. `project-sync` reads these keys from `[github.issues.rules]`.

**What you must do.** If your board uses other column names, map them. If you rely on `Priority`/`Effort` gating, set `priority = true` / `effort = true` to keep the v0.1.0 behaviour.

```toml
# before (v0.1.0): columns had to be named like the canonical statuses;
# Priority and Effort were always required by the Ready gate
[github.project]
number = 4

# after (v0.2.0)
[github.project]
number = 4

[github.project.status_mapping]
"To do" = "Backlog"
"Doing" = "In progress"
"Shipped" = "Done"

[github.issues.rules]
priority = true
effort = true
```

**Later.** The five-status model becomes configuration in the v0.3.0 workflow engine; `[github.project.status_mapping]` is removed (it fails to load); `tools config migrate` drops it when its aliases only repeat the status names and refuses when it renames a column (#88). See [Workflow engine and `tools config migrate`](v0.3.0.md#workflow-engine-and-tools-config-migrate-56-57-58) in the v0.3.0 guide.

## Legacy label migration (#14, #33)

**What changed.** `issues-check` gained a migration mode to bring legacy labels onto the `type:`/`area:` taxonomy:

- `issues-check --migrate` previews the planned label changes; adding `--apply` writes them.
- Built-in mappings: `bug`→`type:fix`, `enhancement`→`type:feat`, `documentation`→`type:docs`, `chore`→`type:chore`, `refactor`→`type:refactor`, `spike`→`type:spike`, `feature`→`type:feat`, `fix`→`type:fix`. Add or override mappings with `[github.labels.migrations]`; `[github.labels.renames]` entries apply too.
- `--default-area <label>` adds a fallback area to issues that have none; `--default-type <label>` (#33) adds a fallback type to issues that have none (`chore` and `type:chore` are both accepted). Both require `--migrate`.

```toml
[github.labels.migrations]
ui = "area:web"
backend = "area:api"
```

```bash
issues-check --migrate --repo web                       # preview
issues-check --migrate --apply --default-type chore --default-area web --repo web
```

**What you must do.** Nothing; migration is opt-in. Run the preview before `--apply`, since `--apply` writes to GitHub. `--migrate` does not run the audit and always exits 0, so a CI step using it checks nothing: keep a separate plain `issues-check` step.

**Later.** v0.3.0 makes migrations config-only and removes `--default-type` and `--default-area` (#61, #62); the `issues-check --migrate` preview becomes part of `tools issues check` and `--migrate --apply` becomes `tools issues migrate`. An unlabeled issue is then fixed by hand or by a `[github.labels.migrations]` entry, not by a fallback flag. See [Label migrations are config-only](v0.3.0.md#label-migrations-are-config-only-61) in the v0.3.0 guide.

## Nested comment and review pagination (#35)

**What changed.** The repository text reader now follows pagination for comments inside review threads and for long comment and review lists, instead of dropping what did not fit in the first page.

**What you must do.** Nothing; there is no configuration or output format change. The text reader fed the reference checks removed in #36, so a v0.2.0 audit shows no visible difference.

## Upgrade checklist

1. Pin the new version: `jaoppb/tools@v0.2.0` or `TOOLS_VERSION=v0.2.0`.
2. Delete `references` and `text` from `[github.issues.rules]`.
3. Set `milestone_format` if your milestones are not `vX.Y.Z`; set `area_prefixes` if you use another prefix.
4. If you target several repositories, list them in `[github] repositories` and run `repo-sync --dry-run` before applying.
5. Run `issues-check` and `repo-sync --check` and confirm they pass.
