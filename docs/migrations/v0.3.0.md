# Migrating from v0.2.0 to v0.3.0

Previous: [v0.1.0 → v0.2.0](v0.2.0.md) · Next: none yet

This guide covers what an adopter of the `v0.2.0` binaries, the composite GitHub Action or `tools.toml` has to know to move to `v0.3.0`. `v0.3.0` is a breaking release: three binaries become one `tools` CLI, the Project workflow moves from hard-coded rules into a `[workflow]` block evaluated by a rule engine, and several keys that `v0.2.0` accepted now fail to load. Where a later release changes something again, the section ends with a **Later** note.

Every release gets one guide, `docs/migrations/<version>.md`, covering the step from the previous release only. Jumping several releases means reading the guides in order.

## If you stay on v0.2.0: pin `version`

**What changed.** Nothing in your repository, but the action's `version` input defaults to `latest`. Once `v0.3.0` is published, `jaoppb/tools@v0.2.0` resolves `latest` to `v0.3.0`, looks for `issues-check-v0.3.0-<target>` assets that no longer exist, and its `cargo install` fallback asks for an `issues-check` package that is gone, so the install step fails.

**What you must do.** Either upgrade with the rest of this guide, or pin both the action and the binary:

```yaml
- uses: jaoppb/tools@v0.2.0
  with:
    version: v0.2.0
```

The same applies to `scripts/install-tools.sh` from a v0.2.0 checkout: set `TOOLS_VERSION=v0.2.0`.

## One `tools` binary (#66)

**What changed.** `issues-check`, `repo-sync` and `project-sync` are replaced by one binary, `tools <group> <verb>`. Read-only verbs are always `check`; writing verbs are `sync` or `migrate`. `--dry-run` is gone everywhere except `tools config migrate`: `check` is the preview. `--config`, `--owner` (alias `--org`, now also for Projects) and `--repo` are global flags.

| v0.2.0 | v0.3.0 | Note |
|--------|--------|------|
| `issues-check` | `tools issues check` | Also previews pending label migrations and exits 1 if any |
| `issues-check --migrate` | `tools issues check` | Also runs the audit; **exits 1 on any violation or pending migration** (`--migrate` always exited 0) |
| `issues-check --migrate --apply` | `tools issues migrate` | Always writes; no `--apply` |
| `repo-sync --check` / `repo-sync --dry-run` | `tools repo check` | **Exits 1 on drift** (`--dry-run` exited 0) and also runs the [offline template and doc check](#issue-templates-and-doc-label-lists-checked-by-repo-check-64) |
| `repo-sync` | `tools repo sync` | `--settings`, `--labels`, `--milestones`, `--project` still limit the scope |
| `project-sync --dry-run` | `tools project check` | **Exits 1 when a card would move or is frozen** (was 0) |
| `project-sync` | `tools project sync` | |
| — | `tools project check --explain <issue>` | Prints the facts and rules behind one card (`57` or `repo#57`) |
| — | `tools config check` / `tools config migrate` | See [the workflow engine](#workflow-engine-and-tools-config-migrate-56-57-58) |

Exit codes are the same for every command: `0` clean, `1` something is left to fix (a `check` found drift, `repo sync` left an `error` item, `config migrate` refused), `2` the run could not complete.

**Release assets.** One archive per target, `tools-v0.3.0-<target>.tar.gz` (`.zip` on Windows) with a matching `.sha256`, for the same five targets as `v0.2.0`.

**Install script.** `scripts/install-tools.sh` installs only `tools`. `TOOLS_LIST` is no longer read, and **the second positional argument changed meaning**: it was the tool list in v0.2.0 and is now the install directory.

```bash
# before (v0.2.0)
TOOLS_VERSION=v0.2.0 TOOLS_LIST="issues-check,repo-sync" ./scripts/install-tools.sh
./scripts/install-tools.sh v0.2.0 "issues-check,repo-sync" "$HOME/bin"

# after (v0.3.0)
TOOLS_VERSION=v0.3.0 ./scripts/install-tools.sh
./scripts/install-tools.sh v0.3.0 "$HOME/bin"
FROM_SOURCE=true ./scripts/install-tools.sh     # build the checkout with cargo instead
```

**Partial builds.** Each group is a cargo feature (`issues`, `repo`, `project`, all on by default); `tools config` is always built: `cargo build -p tools --no-default-features --features repo`.

**What you must do.** Replace every command line, script and CI step with the `tools` form. A CI step that ran `project-sync --dry-run`, `repo-sync --dry-run` or `issues-check --migrate` as an informational preview now fails whenever something is pending; run it with `continue-on-error` if it should stay informational.

## Composite action inputs (#63, #66)

**What changed.** The action installs and runs the single binary, so its inputs follow the commands. Compared with `v0.2.0`:

| v0.2.0 input | v0.3.0 | Meaning |
|--------------|--------|---------|
| `tools` | removed | There is one binary |
| `issues-check-args` | `issues-args` | Extra flags for `tools issues check` |
| `repo-sync-args` | `repo-args` | Extra flags for `tools repo check` |
| `check-issues` | unchanged | Runs `tools issues check` |
| `check-repo` | unchanged | Runs `tools repo check` |
| `version`, `install-dir`, `github-token`, `cache` | unchanged | `installed-version` is `source` with `build-from-source` |
| — | `config-path` | Passed as `--config` to every command the action runs |
| — | `repo` | Repository that publishes the release binaries (default `jaoppb/tools`) |
| — | `check-project` | Runs `tools project check` (exit 1 when a move is pending) |
| — | `sync-project` | Runs `tools project sync`; writing Projects v2 needs a PAT or app token in `github-token`, the default `github.token` cannot |
| — | `project-args` | Extra flags for `tools project check` and `tools project sync` |
| — | `build-from-source` | Builds the binary with cargo from the action's checkout |

If you pinned `jaoppb/tools@main` between #63 and #66, you may have used `project-sync-args`: it is now `project-args`, and `project-sync-args: '--dry-run'` is now `check-project: 'true'`.

**What you must do.** Rename the inputs and pin the release:

```yaml
# before (v0.2.0)
- uses: jaoppb/tools@v0.2.0
  with:
    tools: issues-check,repo-sync
    check-issues: 'true'
    check-repo: 'true'
    issues-check-args: '--repo web'
    github-token: ${{ secrets.GITHUB_TOKEN }}

# after (v0.3.0)
- uses: jaoppb/tools@v0.3.0
  with:
    version: v0.3.0
    check-issues: 'true'
    check-repo: 'true'
    issues-args: '--repo web'
    repo-args: '--repo web'          # skips the doc label check until #93, see below
    config-path: tools.toml          # optional; default is an upward search
    github-token: ${{ secrets.GITHUB_TOKEN }}
```

`version` must name a release that ships `tools` (`v0.3.0` or later); earlier tags only carry the old binaries. `check-repo` runs `tools repo check`, which now also checks local doc files: see [Issue templates and doc label lists](#issue-templates-and-doc-label-lists-checked-by-repo-check-64) before enabling it without `repo-args`.

## Removed rule keys are rejected (#60)

**What changed.** `[github.issues.rules]` refuses unknown keys. `references` and `text`, parsed and ignored since v0.2.0, now fail to load, and so does any misspelled key. Every command that loads the file fails (`tools config migrate` too: it prints ``the migrated tools.toml would not load, nothing was written:`` before the same error, reported against `<memory>` instead of the file name, and exits 2; `tools config check` lists only what `migrate` would rewrite and does not mention these keys):

```
failed to parse config file at tools.toml: TOML parse error at line 7, column 1
  |
7 | references = true
  | ^^^^^^^^^^
unknown field `references`, expected one of `cycle`, `labels`, `membership`, `milestone`, `parent`, `require_parent`, `release`, `priority`, `effort`, `area_prefixes`, `milestone_format`
```

**What you must do.** Delete the keys before running anything else.

```toml
# before (v0.2.0): accepted and ignored
[github.issues.rules]
labels = true
references = true
text = true

# after (v0.3.0)
[github.issues.rules]
labels = true
```

## `unmanaged` replaces `prune_unmanaged` (#76)

**What changed.** The boolean `prune_unmanaged` is replaced by a per-kind severity `unmanaged = "ignore" | "warn" | "error" | "prune"` on `[github.labels]`, `[github.milestones]` and their `[github.overrides.<repo>.*]` overlays. A file that still sets `prune_unmanaged` fails to load, naming the table:

```
tools.toml: `prune_unmanaged` in [github.labels] was removed; set `unmanaged = "prune"` (was true) or `unmanaged = "warn"` (was false)
```

| `unmanaged` | `tools repo check` | `tools repo sync` |
|-------------|--------------------|-------------------|
| `ignore` | says nothing | says nothing |
| `warn` (labels' default) | names each item, exit 0 | names each item, exit 0 |
| `error` (milestones' default) | names each item, exit 1 | applies everything else, names each item, exits 1 |
| `prune` | reports the deletion as drift, exit 1 | deletes the item |

**Unknown keys are rejected.** The shared `[github.labels]` and `[github.milestones]` tables now refuse unknown keys like their overlays already did, so a stray or misspelled key fails to load with a TOML parse error ending in ``unknown field `color_default`, expected one of `deprecated`, `renames`, `unmanaged`, `migrations`, `items` `` (for `[github.milestones]` the list has no `migrations`).

**Default changed for milestones.** In v0.2.0 an undeclared milestone was listed as unmanaged and `repo-sync --check` still passed. In v0.3.0 milestones default to `error`, open and closed alike, so **every milestone on GitHub that is not in `[github.milestones].items` fails `tools repo check`**. Old closed releases are the usual culprit.

**What you must do.** Replace the key and delete any other key these tables do not list, then declare your existing milestones (or list them under `deprecated` to delete them), or relax the default:

```toml
# before (v0.2.0)
[github.labels]
prune_unmanaged = true

[github.milestones]
items = [{ title = "v0.2.0", description = "Current release", state = "open" }]

# after (v0.3.0)
[github.labels]
unmanaged = "prune"                # prune_unmanaged = false becomes "warn" (the default)

[github.milestones]
unmanaged = "error"                # the default; "warn" restores the v0.2.0 tolerance
items = [
    { title = "v0.1.0", description = "First release", state = "closed" },
    { title = "v0.2.0", description = "Current release", state = "open" },
]
```

## Workflow engine and `tools config migrate` (#56, #57, #58)

**What changed.** `tools project` no longer has the Project workflow built in. Statuses, facts and rules are data in a `[workflow]` block, written as [CEL](https://cel.dev) expressions and evaluated first match wins: local rules in file order, then the preset's. Two presets ship:

- `builtin:cosmo`: epic/story/task, a task waits for its story, Ready gate of type, area, milestone, **Priority and Effort** (Effort ≤ `params.effort_limit`, 8), no open blockers.
- `builtin:tools`: standalone issues, Ready gate of type, area, milestone and no open blockers; no Priority/Effort, parent, epic or membership.

Both declare the statuses `Backlog`, `Ready`, `In progress`, `In review`, `Done`. A local block overrides a preset: `[workflow.params]` merges over the preset's params, a `[workflow.facts]` entry replaces the preset fact of the same name, and a `[[workflow.status]]` rule that reuses a preset rule's `id` drops that preset rule (the local one still runs before every preset rule). The fact schema and the rule semantics are in [the workflow engine spec](../workflow-engine-spec.md).

Consequences for v0.2.0 files:

- `[github.project.status_mapping]` is **removed**. Board columns must equal `[workflow].statuses` exactly (trimmed, case-sensitive). v0.2.0 matched columns case-insensitively, so a board column `In Progress` that needed no mapping before is now an unknown column; rename it on the board. A case-only alias such as `"In Progress" = "In progress"` counts as a rename, so `migrate` refuses it. A file that still has the key fails to load for every command: ``tools.toml: [github.project.status_mapping] was removed; board columns must equal [workflow].statuses. Run `tools config migrate` to rewrite the file``.
- `tools project check|sync` refuse to run without `[workflow]`: ``no [workflow] block in tools.toml: add `[workflow]` with `extends = "builtin:cosmo"` or `"builtin:tools"`, or declare your own statuses and rules``.
- `[github.issues.rules]` is **deprecated**, not removed: `tools issues check` still reads it (until the audit moves to the workflow in v0.4.0, #59) and prints a deprecation warning. `tools project` no longer reads it, so its `priority`, `effort`, `parent`, `membership`, `area_prefixes` toggles have no effect on the board any more.
- `params.area_prefix` is a **list** (`["area:"]` by default). Matching ignores case and accents as before.
- A file **without a `[github.issues.rules]` table** (v0.2.0 defaults) gets no `[workflow]` from `migrate`: `tools config check` and `migrate` both report `nothing to migrate` (or only the `status_mapping` removal), and `tools project check` then refuses to run. Following that error's hint with a bare `extends = "builtin:cosmo"` gives the [strict gate](#strict-builtincosmo-gate-57). To keep the v0.2.0 gate, add an empty `[github.issues.rules]` table and run `migrate`, or write the result yourself:

  ```toml
  [workflow]
  extends = "builtin:cosmo"

  [workflow.facts]
  triaged = "has_type && has_area && issue.milestone != null"
  ```

**What you must do.** Run the one-shot migration. It rewrites `tools.toml` in place with comments kept, is idempotent, and leaves `[github.issues.rules]` for the audit. Delete `references`/`text` and `prune_unmanaged` first: `migrate` re-loads the file it writes, and refuses (exit 2, nothing written) when another removed key makes it fail.

```bash
tools config check              # what is pending; exit 1 until migrated
tools config migrate --dry-run  # the notes and the new file, nothing written
tools config migrate            # write it
```

How the old keys map:

| v0.2.0 | v0.3.0 |
|--------|--------|
| `parent = false` and `membership = false` | `extends = "builtin:tools"` |
| anything else | `extends = "builtin:cosmo"` |
| `priority`/`effort` both on with `builtin:cosmo` | nothing (the preset gate is already strict) |
| `priority` or `effort` off with `builtin:cosmo` (the v0.2.0 default) | a local `triaged` fact keeping only the enabled terms |
| `priority` or `effort` on with `builtin:tools` | a local `triaged` fact; `effort` also adds `params.effort_limit = 8` |
| `area_prefixes` other than `["area:"]` | `[workflow.params] area_prefix` |
| `milestone_format` other than `"semver"` | `[workflow.params] milestone_format` (read by the v0.4.0 audit, #59) |
| `status_mapping` whose aliases repeat the status name | removed |
| `status_mapping` that renames a column | **refused**, see below |

**Example: a typical v0.2.0 file.** Default toggles (so `priority` and `effort` off), a second area prefix, and a `status_mapping` that only repeats canonical names:

```toml
[github.repository]
owner = "acme"
name = "web"

[github.project]
number = 4

# Every alias repeats a canonical name, so nothing is renamed.
[github.project.status_mapping]
"Backlog" = "Backlog"
"In progress" = "In progress"

[github.issues.rules]
labels = true
milestone = true
release = true
cycle = true
area_prefixes = ["area:", "domain:"]
```

```
$ tools --config tools.toml config check
tools.toml: [github.project.status_mapping] is removed: board columns must equal [workflow].statuses
tools.toml: [github.issues.rules] has no [workflow] equivalent yet
run `tools config migrate` to rewrite the file
$ echo $?
1
$ tools --config tools.toml config migrate
migrated tools.toml
- removed [github.project.status_mapping] (every alias repeated its status name)
- added [workflow] extends = "builtin:cosmo" (parent = true, membership = true)
- area_prefixes -> [workflow.params] area_prefix
- priority = false, effort = false -> [workflow.facts] triaged shadows the preset gate
$ tools --config tools.toml config check
tools.toml: nothing to migrate
[github.issues.rules] is deprecated and stays until #59 (the issue audit still reads it)
$ tools --config tools.toml config migrate
tools.toml: nothing to migrate
```

The converted file:

```toml
[github.repository]
owner = "acme"
name = "web"

[github.project]
number = 4

[github.issues.rules]
labels = true
milestone = true
release = true
cycle = true
area_prefixes = ["area:", "domain:"]

[workflow]
extends = "builtin:cosmo"

[workflow.params]
area_prefix = ["area:", "domain:"]

[workflow.facts]
# Ready gate of the old toggles (priority = false, effort = false); builtin:cosmo alone requires both Priority and Effort.
triaged = "has_type && has_area && issue.milestone != null"
```

Until #59, `area_prefixes` (read by `tools issues check`) and `params.area_prefix` (read by `tools project`) are separate: change both if you change one.

**Example: a `status_mapping` that renames columns.** The engine has no column aliases yet (#88), so `migrate` refuses and writes nothing. The same file as above, with these tables instead:

```toml
# [github.repository] and [github.project] as in the first example
[github.project.status_mapping]
"To do" = "Backlog"
"Doing" = "In progress"
"Shipped" = "Done"

[github.issues.rules]
priority = true
effort = true
```

```
$ tools --config tools.toml config migrate
[github.project.status_mapping] renames board columns ("To do" = "Backlog", "Doing" = "In progress", "Shipped" = "Done"); the board columns must now equal [workflow].statuses and the engine has no column aliases yet (see #88). Rename the columns on the board to the canonical names, then drop the key; nothing was written
$ echo $?
1
```

Rename the columns on the board (`To do` → `Backlog`, `Doing` → `In progress`, `Shipped` → `Done`), delete the `status_mapping` table, and run `migrate` again. With both toggles on, the preset gate already matches, so only `extends` is added:

```
$ tools --config tools.toml config migrate --dry-run
- added [workflow] extends = "builtin:cosmo" (parent = true, membership = true)
```

The whole new file follows that note; the part it adds is:

```toml
[workflow]
extends = "builtin:cosmo"
```

**Writing `[workflow]` by hand.** A param you override keeps the type of the preset's value: `area_prefix` and `started` are lists of strings, `type_prefix` and `epic_label` strings, `effort_limit` an integer (`8.5` or `"8"` is refused). A mismatch fails to load with the line and column of your value, for example `line 9, column 15: param "area_prefix": the preset has a list of strings, this is a string`. `tools config check` reports a single value where the preset has a list (`area_prefix = "area:"`, the shape on `main` before #58) and `tools config migrate` wraps it:

```toml
# before
[workflow.params]
area_prefix = "area:"

# after
[workflow.params]
area_prefix = ["area:"]
```

A rule or fact that fails while a card is evaluated freezes that card only (`<issue> frozen: rule "x" failed: ...`), and so does a crash inside the CEL interpreter (`<issue> frozen: rule "x" panicked in the interpreter: ...`); the run goes on with the other cards.

## Strict `builtin:cosmo` gate (#57)

**What changed.** `tools project` runs on the engine. This section supersedes the interim changelog in [the workflow engine spec](../workflow-engine-spec.md#changelog-what-moves-under-the-strict-builtincosmo-gate-v030). Compared with `project-sync` under v0.2.0's default rules (Priority and Effort off):

- `builtin:cosmo` alone makes a card **Ready only with Priority and Effort set** and Effort ≤ 8. `tools config migrate` writes a `triaged` fact that keeps your v0.2.0 gate; a hand-written `extends = "builtin:cosmo"` without it sends every not-started Ready card lacking Priority or Effort, or with Effort above 8, back to `Backlog` on the first `sync`. Started cards (`In progress`, `In review`) are never demoted.
- A task whose **story is not on the Project** now waits for that story (the story is fetched on demand); before, it was never held.
- A parent the token cannot read, or a parent in a repository the token cannot read, **freezes** the card: no move, reported.
- Board columns must equal `[workflow].statuses` exactly; an unknown column is an error naming it.
- Output is one line per decision: `<issue> A -> B (<rule-id>)` for a move, `<issue> frozen: <cause>` for a frozen card, then `N kept, M moved, K frozen`. The reason is the id of the rule that fired (`gate-holds`, `gate-closed`, …) instead of prose; gap lines ("needs triage") are no longer printed, `tools issues check` still reports missing labels and milestones.

**What you must do.** Before the first `sync`, preview and read every move:

```bash
tools project check                 # exit 1 while a move is pending or a card is frozen
tools project check --explain 42    # why issue 42 moves: every fact and rule, and which fired
tools project sync
```

To keep a stricter or looser gate, shadow `triaged` in `[workflow.facts]` or override `params.effort_limit`; see the spec for the fact schema.

## Parent cycles freeze cards (#65)

**What changed.** In v0.2.0 a parent cycle between stories overflowed the stack and crashed `project-sync`. In v0.3.0 the engine detects the cycle before evaluating: every card on it, and every card below a frozen parent, gets no move and is reported as frozen. `tools project check` exits 1 while such a card exists; `sync` exits 0 after writing the other moves.

**What you must do.** Nothing. If `check` reports a frozen card, break the cycle in the issues' parent links.

## Label migrations are config-only (#61)

**What changed.** The built-in legacy label map (`bug`, `enhancement`, `documentation`, `chore`, `refactor`, `spike`, `feature`, `fix`) is gone, and `[github.labels.renames]` no longer feed issue migrations: a rename renames the label itself on GitHub, nothing more. The shared `[github.labels.migrations]` table is the only source; `migrations` in a `[github.overrides.<repo>.labels]` overlay are not applied by any command (they were not in v0.2.0 either). With no configuration, nothing is remapped.

`tools issues check` now ends with the pending migrations and **exits 1 while any remain**, so a CI audit fails as long as an open issue carries a label your map converts.

**What you must do.** Declare every mapping you relied on, including the former built-ins:

```toml
# before (v0.2.0): the eight built-ins and every rename applied implicitly
[github.labels.migrations]
ui = "area:web"

# after (v0.3.0): only what is listed here
[github.labels.migrations]
bug = "type:fix"
fix = "type:fix"
enhancement = "type:feat"
feature = "type:feat"
documentation = "type:docs"
chore = "type:chore"
refactor = "type:refactor"
spike = "type:spike"
ui = "area:web"
```

```bash
tools issues check      # audit, then the pending migrations
tools issues migrate    # write them
```

## Fallback label flags removed from `issues migrate` (#62)

**What changed.** `--default-type` and `--default-area` are gone. `tools issues migrate` only applies `[github.labels.migrations]`; it never invents a label. The `[workflow]` rules cannot replace them either: a rule sets a Project status, it does not edit labels.

**What you must do.** Drop the flags. `tools issues check` lists the issues still missing a type or area label; label them by hand or with `gh issue edit <n> --add-label type:chore`.

```bash
# before (v0.2.0)
issues-check --migrate --apply --default-type chore --default-area web --repo web

# after (v0.3.0)
tools issues migrate --repo web
tools issues check --repo web      # remaining unlabeled issues
```

**Later.** Label management through workflow rules is planned for v0.4.0 (#78).

## Issue templates and doc label lists checked by `repo check` (#64)

**What changed.** `tools repo check` starts with an offline step that compares local files with `tools.toml`, before any GitHub call. It runs when you check one repository without `--owner`/`--repo` and without a scope flag that excludes labels, and fails with exit 1 on any problem:

- **Issue templates**, only when `[github.issue_templates]` is declared: each entry's file under `.github/ISSUE_TEMPLATE/` must exist, its `labels:` must be exactly the entry's label (a label declared for the repository), and its `title:` must start with the entry's prefix. With `require_label = true` (the default), every template file except `config.yml` needs an entry.
- **Doc label lists**, always: `AGENTS.md` and `CONTRIBUTING.md` next to `tools.toml` must each contain a `<!-- labels:start -->` … `<!-- labels:end -->` block whose bullets starting with a backticked name list exactly the labels declared for the repository: `[github.labels].items` plus the items of its `[github.overrides.<repo>.labels]` overlay.

```toml
[github.issue_templates]
require_label = true
items = [
    { file = "feat.yml", label = "type:feat", title = "feat: " },
    { file = "fix.yml", label = "type:fix", title = "fix: " },
]
```

```markdown
<!-- labels:start -->
- `type:feat` — New behaviour or capability
- `type:fix` — Something is broken
<!-- labels:end -->
```

**The doc step is not optional yet.** A repository without both files fails `tools repo check`, and so does the action's `check-repo`:

```
AGENTS.md: cannot read: No such file or directory (os error 2)
CONTRIBUTING.md: cannot read: No such file or directory (os error 2)
```

This is fixed by #93, which makes the step opt-in. Until then, either add both files with a label block, or pass the repository explicitly (`tools repo check --repo <name>`, or `repo-args: '--repo <name>'` in the action), which skips the offline step.

**What you must do.** Declare `[github.issue_templates]` if you want your templates checked, and handle the doc step as above. Milestone lists no longer belong in docs or templates: `[github.milestones]` is their only home.

## For maintainers and forks: release flow (#52)

This only matters if you release this repository or a fork; adopters of the CLI or the action can skip it.

**What changed.** `just bump-version` no longer pushes to `main`. `just bump-version <major|minor|patch|X.Y.Z> --issue <n> [--dry-run]` checks its preconditions (authenticated `gh`, clean tree, local `main` at `origin/main`, tag and branch free, a strictly greater version), creates `chore/<n>`, bumps `Cargo.toml`/`Cargo.lock`, pushes and opens the PR. When that PR merges, the `Tag Release` workflow tags the merge commit `vX.Y.Z` and calls `Release`, which checks the tag against the `Cargo.toml` version and publishes the binaries. Pushing a `vX.Y.Z` tag by hand still triggers `Release` directly.

**What you must do.** File a `type:chore` issue for the bump, run the recipe, merge the PR. If `Release` fails after the tag exists, re-run the failed jobs of the same `Tag Release` run. The recovery steps are in [CONTRIBUTING.md, "Releasing"](../../CONTRIBUTING.md#releasing).

**Later.** #91 hardens `Tag Release` (tag only when the push changed the version, an explicit `workflow_dispatch` recovery) before the v0.3.0 bump; CONTRIBUTING.md documents it once merged.

## Upgrade checklist

0. Install `tools` v0.3.0 locally to run the steps below (from a v0.3.0 checkout of this repository: `TOOLS_VERSION=v0.3.0 ./scripts/install-tools.sh`; the v0.2.0 script cannot install it); step 5 updates CI.
1. Delete `references`/`text` from `[github.issues.rules]` and any key `[github.issues.rules]`, `[github.labels]` or `[github.milestones]` no longer accepts; replace `prune_unmanaged` with `unmanaged`.
2. Run `tools config check`, then `tools config migrate`. If it refuses on `status_mapping`, rename the board columns to the `statuses`, delete the table and run it again. If the file has no `[github.issues.rules]` table, add an empty one first (or write `[workflow]` by hand).
3. Declare every milestone that exists on GitHub (or set `[github.milestones] unmanaged = "warn"`), and every label migration you relied on in `[github.labels.migrations]`.
4. Add the `AGENTS.md`/`CONTRIBUTING.md` label blocks, or check with `--repo` until #93 lands.
5. Replace the binaries and commands with `tools` (`jaoppb/tools@v0.3.0` with `version: v0.3.0`, or `TOOLS_VERSION=v0.3.0`), and rename the action inputs.
6. Run `tools issues check`, `tools repo check` and `tools project check`; read every planned move (`--explain` when one surprises you) before `tools project sync`.
